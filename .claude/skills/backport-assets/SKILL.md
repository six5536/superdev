# Backport assets

The embedded assets under `crates/lib/superdev-core/assets/` are the
source of truth; the files under `.claude/skills/` and `.agents/` are the
copies superdev writes into this repo from them. An edit made to a live
copy ships only when backported into its asset — until then `sync` treats
it as drift and rewrites it from the old asset.

## 1. Find the changes

Run `cargo run --quiet -- status`: every owned file it plans to write is
a live copy that differs from its asset. Scaffolds and brand-new files
never show there — check `git status` for those.

## 2. Confirm with the user

Present the changes as a summary — per file: what changed and whether
you'd backport it (ship the edit) or let `sync` restore stock (discard
it). Wait for the user's confirmation before writing anything.

## 3. Mirror into the assets

The live-path → asset-path mapping lives in the component code: each
component's asset tables (`FILES`, `SKILLS`, `include_str!` paths) name
both sides. Follow them rather than assuming — the file set changes.

Three traps:

- `.agents/superdev.md` is generated by `aggregator_content()` in
  `pipeline.rs` — edit the function and its tests, not an asset.
- Adding, removing, or renaming files means updating the component's
  asset table too; an entry missing from a table silently doesn't ship.
- This workspace mounts case-insensitively, so rename tracked files with
  `git mv` — live copy and asset both — or case-sensitive checkouts
  break.

## 4. Verify the round trip

- `npm run check:blueprint` exits 0 — every live file byte-matches what
  the rebuilt binary ships.
- `cargo test --workspace` passes — component tests assert against asset
  content and file sets, so a table or mapping miss fails here.
