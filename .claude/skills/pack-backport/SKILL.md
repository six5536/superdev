# Pack-backport mode

You are in pack-backport mode. You are a release engineer: you mirror
edits made to this repo's live skills, agent files and document
templates into the pack they ship from.

`/pack/` is the source of truth; the files under `.claude/skills/`,
`.agents/` and `knowledge/templates/` are the copies superdev writes
into this repo from it. This repo pins `/pack/` as a local-path pack,
so a backported edit lands on the next `sync` with **no rebuild** — and
until it is backported, `sync` treats the live edit as drift and
rewrites it from the pack.

Reached from the crate as `crates/lib/superdev-core/assets/`, which is a
symlink to `/pack/` (ADR-006). Edit `/pack/`.

## Input

- $ARGUMENTS — the files or changes to backport, when given.

## Workflow

- [ ] Find the changes: `cargo run --quiet -- status` lists every owned
      file that differs from the pack. Scaffolds and brand-new files
      never show there — check `git status` for those.
- [ ] GATE: Present the changes — per file: what changed, and whether
      you would backport it (ship the edit) or let `sync` restore stock
      (discard it). Wait for the user's confirmation before writing
      anything.
- [ ] Mirror into `/pack/`, by the table below.
- [ ] Make the code changes the change needs, if any — see **When code
      has to change**. Most backports need none.
- [ ] Verify the round trip: `cargo run --quiet -- sync` writes the live
      copies back with no diff, `npm run check:blueprint` exits 0, and
      `cargo test --workspace` passes.
- [ ] Refresh the lock for each file you backported: delete the live
      file and `sync` again, which rewrites and re-records it. See
      **The lock does not refresh itself** for why.

## Where each live file comes from

The pack's layout is what names its items (ADR-003), so the slot decides
the path. When a file already exists in the pack, mirror it back to
where it is rather than deriving the path:

| Live | Pack |
|------|------|
| `.claude/skills/<name>/**` | `pack/knowledge/skills/<name>/**` — the workflow and support skills |
| `.claude/skills/<name>/**` | `pack/skills/<name>/**` — only the three skills the `skills` capability ships |
| `.agents/<file>.md` | `pack/agents/<file>.md` |
| `knowledge/templates/<file>.md` | `pack/knowledge/templates/<file>.md` |
| a knowledge scaffold | `pack/knowledge/concepts/<name>` |

`pack/projects/**` is not this skill's: a project template is harvested
from an exemplar by `template-backport`, which is the other direction.

## When code has to change

Adding, removing or renaming a pack file needs **no table edit**:
`crates/lib/superdev-core/build.rs` walks the tree and generates the
file list, so the layout is the only declaration. What still needs code:

- `.agents/superdev.md` is generated by `aggregator_content()` in
  `pipeline.rs`. Edit the function and its tests, never a pack file.
- A new *kind* of item — not a new item of a kind that exists — needs a
  rule in `classify()` in `content/layout.rs`, and an `ItemKind`.
- A test that names specific content (several in `content/` use `frame`
  as their example) fails if you rename what it names.

## The lock does not refresh itself

A hash is recorded only for a file superdev *writes*. A backport ends
with the live copy already matching the pack, so `sync` writes nothing
and the lock keeps the hash from before your edit
([I005](/knowledge/issues/I005-a-backport-leaves-the-lock-stale.md)).
Nothing is broken by it now, but the next run that does write that file
reports `overwrote a user-edited file (backed up)` and backs up a file
nobody edited — and the backup pile is how this repo's older stale
entries accumulated.

Repair it in the same pass:

```sh
rm .claude/skills/<name>/SKILL.md && cargo run --quiet -- sync
```

Delete the **file**, never its directory: a skill directory may hold a
repo-owned `PROJECT.md` that superdev does not ship and cannot put back.

## IMPORTANT RULES

- Deleting from `/pack/` does **not** remove the live copy. A local pack
  layers, so it can add and supersede but never take away
  ([I003](/knowledge/issues/I003-a-local-pack-cannot-remove-what-it-dropped.md));
  the live file goes only on a rebuild. Say so rather than reporting a
  removal that did not happen.
- This workspace mounts case-insensitively: rename tracked files with
  `git mv` — live copy and pack both — or case-sensitive checkouts
  break.
- Run `sync` when you are done. The live skills are superdev-owned, so
  an edit left unbackported is overwritten (and backed up) by the next
  one anybody runs.
- Any commit touching `pack/` should be made with `sync` run: the lock
  records a digest over the whole tree
  ([I004](/knowledge/issues/I004-a-path-packs-digest-churns-and-is-never-checked.md)).

## Output

- The pack, matching the live copies, with the round trip green.

## Project adaptations

If a `PROJECT.md` exists in this skill's directory, read it now and apply
it; where it conflicts with this file, `PROJECT.md` wins. If absent,
continue.
