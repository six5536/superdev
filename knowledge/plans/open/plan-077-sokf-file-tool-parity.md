# Plan: SOKF-routed file tools match Pi's built-in contracts

## Goal and boundaries

Implement [SOKF-routed file tools match Pi's built-in contracts][sokf:issue-077-sokf-file-tool-parity]. A physical file path and its `sokf:<id>` alias must expose the same Pi 0.85.1 file-tool behavior. SOKF adds identity routing, agent-safe policy, repair, refiling, and validation only. A mutation acknowledged with `applied: true` remains successful: SOKF retains the requested bytes and every successful automatic repair, returns Pi's normal file-tool result unchanged, and reports remaining validation findings in a separate visible turn-end follow-up that triggers targeted correction. An indeterminate local MCP failure with no authoritative response remains a tool error that requires manual inspection and validation.

The installed Pi factories, operations interfaces, result types, renderers, argument preparation, `generateDiffString()`, `generateUnifiedPatch()`, `withFileMutationQueue()`, `turn_end`, and `pi.sendMessage()` follow-up delivery are the executable references. The adapter must delegate to those interfaces or use a narrow adapter proven byte-for-byte against them. The SOKF Model Context Protocol (MCP) contract is unreleased, so this plan deliberately changes its mixed retrieval/file-read boundary instead of preserving `sokf_read` compatibility. MCP changes must remain limited to source routing, semantic retrieval separation, parity-safe mutation transport, and bounded diagnostics. The work excludes approximate copies of Pi algorithms, a semantic result dialect in Pi's `read` slot, automatic whole-file recovery after an edit mismatch, validation content inside file-tool results, rollback after acknowledged persistence, durable mutation-outcome reconciliation, weakened SOKF policy, a new extension packaging model, and the general validator symlink walk tracked by issue-031.

## Requirements

The implementation must satisfy the following settled requirements.

- `read path="sokf:<id>"` must resolve the identity to its canonical repository-relative path and return the exact UTF-8 source bytes through Pi's built-in read behavior.
- Routed reads must preserve 1-indexed `offset` and `limit`, 2,000-line and 50 KB head truncation, continuation messages, `ReadToolDetails.truncation`, access errors, out-of-range errors, cancellation, metadata, and rendering.
- Pi's file `read` must reject `sokf:` overview and section-qualified addresses with concise guidance.
- MCP must remove the mixed-purpose `sokf_read` tool. A new `sokf_resolve_source` tool must accept an unqualified `sokf:<id>` or a physical knowledge path. The Pi adapter must apply a narrow path-preparation adapter before calling the resolver. Paired tests must prove its output byte-for-byte against the path values observed at Pi 0.85.1 factory operation boundaries; the adapter must not deep-import unexported package internals. Read routing must preserve `resolveReadPathAsync()` handling for one leading `@`, `~`, Unicode spaces, macOS AM/PM spacing, Normalization Form D (NFD), curly quotes, and combined variants. Edit and write routing must preserve `resolveToCwd()` handling for one leading `@`, `~`, Unicode spaces, and `ctx.cwd`. The resolver must return the repository-relative `knowledge/` ingress path, canonical repository-relative target, existence, and generated-authority metadata without semantic content. An existing regular file must return `exists: true`. A missing physical destination must canonicalize its nearest existing ancestor, append the normalized missing suffix, retain a logical ingress under `knowledge/`, keep its canonical target inside the repository, and return `exists: false`. An existing or ancestor symlink that resolves to a file or directory inside the repository must use the contained target, including a target outside `knowledge/`. A symlink that resolves outside the repository, including one followed before a missing suffix, must fail containment before any read or mutation. Direct physical arguments outside `knowledge/`, missing identities, overview addresses, section-qualified addresses, and directories must remain errors. Generated projections must resolve for reads while naming the authoritative source; mutation routing must reject the generated target before persistence.
- MCP must expose semantic overview, rendered-concept, and section retrieval as `sokf_retrieve`. `sokf_retrieve` must retain the current semantic output and line-window behavior for those address forms, refuse physical file paths, and require no `sokf_read` compatibility alias or deprecation period.
- Routed edits must preserve Pi's current `edits[]` schema, legacy argument preparation, non-empty validation, exact-then-normalized matching, one-snapshot uniqueness and overlap checks, byte-order mark and line-ending preservation, cancellation, and error wording where SOKF policy does not intervene. For `sokf:<id>`, a narrow render wrapper must give Pi's inherited preview renderer the resolved canonical path while keeping Pi's diff implementation unchanged. Preview and renderer evidence may normalize canonical-versus-virtual path spelling.
- The routed edit must resolve the canonical target before invoking Pi's edit factory. Pi's `EditOperations` must read the exact source and submit the computed final content through an agent-safe compare-and-swap mutation carrying the ingress path, expected canonical target, and exact original content. MCP must re-resolve the ingress immediately before policy checks and reject canonical-target drift or stale original content without changing any file.
- A routed edit acknowledged with `applied: true` must return Pi's normal `Successfully replaced N block(s) in PATH.` content and Pi-compatible `EditToolDetails` unchanged. The details must contain Pi's compact display diff, standard unified patch, and `firstChangedLine` for the requested edit.
- A routed write acknowledged with `applied: true` must return Pi's normal `Successfully wrote to PATH` content, `details: undefined`, metadata, and rendering unchanged. Routed writes must also preserve `{ path, content }`, recursive parent creation, cancellation, and errors before persistence. Writing content byte-identical to an existing target must perform the write, return `applied: true`, return Pi success, and schedule final validation.
- Pre-persistence failures include resolution, argument preparation, edit matching, compare-and-swap, agent-safe policy, generated ownership, cancellation before dispatch, and an authoritative persistence response that establishes `applied` is not true. Each pre-persistence failure must return the applicable Pi or concise SOKF tool error, leave every target unchanged, create no applied-mutation state, and schedule no final validation.
- Once an edit or write dispatches MCP persistence, the adapter must stop forwarding the tool abort signal to that mutation request. The adapter must keep the canonical target queue locked until persistence, repair, refiling, and mutation-state capture settle.
- When a mutation returns `applied: true`, SOKF must retain the requested persisted bytes and every automatic repair or refiling change that persisted successfully. A later repair, validation, lifecycle, or cancellation finding must not roll back any persisted file.
- After acknowledged `applied: true`, the adapter must record changed paths and pending final-validation state before resolving the custom persistence operation. The adapter must return the normal successful Pi edit or write result even if the caller aborts after persistence dispatch or post-persistence repair or validation reports findings. It must never convert an acknowledged applied mutation into a tool error.
- When shielded persistence fails with no acknowledged `applied: true`, the adapter must propagate the mutation failure. A concurrent tool abort must not replace that failure. If the local MCP transport or process fails after bytes may have changed but before returning an authoritative outcome, the error must direct the caller to inspect the target and run `superdev validate`. The implementation must not add durable mutation identity or outcome reconciliation.
- Virtual and physical aliases must use the same canonical physical target as the `withFileMutationQueue()` key. The queue must cover each complete read-modify-write window, including shielded post-dispatch persistence and automatic repair.
- Agent-safe mutations must continue to preserve `id` and existing `verified` bytes when present, reject stamped fields, require the direct physical argument or virtual identity to enter through `knowledge/`, keep canonical symlink targets inside the repository, and run repair, refiling, and validation. Bundle discovery must traverse repository-contained directory symlinks under their logical `knowledge/` ingress paths, process each canonical file once, break directory cycles by canonical identity, prefer a direct ingress over a symlink ingress and otherwise the lexically first ingress for duplicate targets, repair the canonical target without replacing its ingress symlink, and refile the logical ingress alias while leaving the canonical target in place.
- Edits intersecting generated projections must fail before mutation and name the authoritative source. The adapter must never recommend or perform an automatic whole-file fallback after a targeted-edit failure.
- MCP `sokf_edit` must act only as the compare-and-swap source transport described below. The Pi `edit` schema must remain the only model-facing file-edit dialect. MCP mutation state and bounded findings must remain available extension-side, while mutation JSON, full repair reports, validation dumps, and duplicate or whole-file patches must not enter file-tool model content.
- After acknowledged `applied: true`, repair or validation problems are findings, not file-tool errors. The mutation result must carry changed-path summaries and actionable findings so the extension can complete the Pi result before reporting validation separately. The complete diagnostic payload must stop at 200 lines or 8 KiB, whichever occurs first, omit patches and mutation envelopes, and direct a caller to `superdev validate` when truncated. A validation execution failure or unknown result must become a concise actionable finding.
- Validation follow-up state must be repository-scoped and use these durable states: `clean`; `pending-auto(n)` for a validation due at the next `turn_end` after `n` triggered follow-ups, where `n` is 0, 1, or 2; `manual` after the automatic cap with no validation due; and `pending-manual` after a manual-state mutation with one validation due. A transient validation guard must prevent two `turn_end` handlers from validating the same state concurrently.
- An `applied: true` mutation in `clean` must enter `pending-auto(0)`. Further applied mutations in any pending state must merge changed paths and findings without resetting `n`. Pre-persistence failures must not change follow-up state. The next `turn_end` in `pending-auto(n)` must run final validation exactly once, even when the preceding correction turn made no applied mutation.
- A valid final-validation result must enter `clean` and clear the follow-up count, changed paths, and findings. An invalid or unknown result, including validation execution failure, must always yield an actionable finding. If `n` is less than 2, the extension must send one visible `sokf-validation` custom message with `{ deliverAs: "followUp", triggerTurn: true }`, increment `n`, and validate again at the triggered correction turn's `turn_end`. If `n` is 2, the extension must enter `manual` and send bounded visible guidance with `triggerTurn: false`.
- An applied mutation in `manual` must enter `pending-manual` without restoring the automatic allowance. Applied mutations in `pending-manual` must coalesce without changing state. At the next `turn_end`, `pending-manual` must run one final validation. A valid result must enter `clean`. A remaining failure must return to `manual` and send one non-triggering manual guidance message for that attempted correction. A mutation, a failed validation, cancellation, compaction, reload, resume, fork, or tree navigation must never reset the automatic allowance. Only a valid final-validation result or a new session with no inherited active-branch state may reset it.
- The extension must append a bounded non-context state snapshot before each externally observable transition and reconstruct the latest snapshot on the active branch at `session_start` and `session_tree`. Reload, resume, fork, and compaction must therefore retain pending work and the follow-up count. A snapshot left pending across shutdown must cause one validation at the next eligible `turn_end`; reconstruction must never resend a follow-up already recorded as sent. If snapshot persistence fails after acknowledged `applied: true`, the adapter must preserve Pi's file-tool success, retain pending validation in memory, and send separate bounded non-triggering guidance to inspect the target and run `superdev validate`. The adapter must not place the snapshot error in file-tool content or details.
- Each visible validation follow-up must contain only concise paths, locations when available, messages, and corrective actions. It must omit patches and mutation envelopes, stop at 200 lines or 8 KiB, whichever occurs first, and direct the agent to `superdev validate` when truncated. Non-context state entries must obey the same bounds.
- `read`, `edit`, and `write` must retain Pi's built-in prompt snippets, baseline guidelines, descriptions, schemas, and renderers. Prompt metadata must add only these flat SOKF rules: `sokf_search: use it when no concept ID is known; otherwise read sokf:<id>.`, `edit: use sokf:<id> for an existing knowledge concept; section addresses are read-only.`, and `write: create a knowledge concept at its physical knowledge/...md path.`
- `sokf_search` and `sokf_graph` must own the two added Available-tools descriptions: `Search canonical project knowledge by meaning` and `Follow relationships between canonical knowledge concepts`.
- A paired harness must compare built-in and routed content, details, thrown errors, resulting bytes, and renderer inputs exactly. The repository must pin `@earendil-works/pi-coding-agent` 0.85.1 as a test dependency, and absence of Pi must fail rather than skip parity tests. The harness may normalize only unavoidable canonical-physical-versus-virtual target spelling, including canonical preview input. It must execute from both the repository root and a nested working directory, and it must cover Pi's accepted leading-`@` path spelling.
- The harness must cover success, failure, offset, limit, both truncation limits, a single oversized line, byte-order marks, CRLF, Unicode, normalized matching, duplicate matches, overlap, multiple disjoint edits, creation, overwrite, and nested parent creation. For both edit and write, deterministic barriers must cover abort before persistence dispatch, abort after persistence returns `applied: true`, abort concurrent with failed persistence, successful repair followed by invalid validation, and post-persistence repair or validation failure.
- A copied routed-read excerpt, including frontmatter, must work unchanged as edit `oldText`. A one-line edit to a large concept must produce the same model-visible result bytes as the paired built-in edit after path normalization.
- Existing shipped and materialized copies must remain synchronized. Repository inspection found only `.pi/skills/sokf-authoring/SKILL.md` mirrored under `pack/pi/skills/`; the project-local SOKF adapter has no pack copy or `.superdev/lock.toml` claim.
- BUILD must remove `/SOKF-EDIT-RELIABILITY-PLAN.md` only after the canonical issue, plan, contracts, ADR, tests, and documentation capture its requirements.

## ADR decisions

- `adr-053-sokf-file-tools-delegate-to-pi`: this SCOPE proposal records that SOKF resolves identities before execution, delegates file semantics and presentation to Pi factories and exported helpers, and permits only byte-proven narrow adapters where package exports do not expose preparation or presentation seams. Queue by canonical physical target, commit edits through an agent-safe compare-and-swap source transport, and keep lifecycle diagnostics outside model-visible file-tool content. Define acknowledged `applied: true` as the adapter outcome boundary: failures with no authoritative applied response remain tool errors, while `applied: true` retains the requested bytes and every successful automatic repair and requires Pi's unchanged success result. Record that an indeterminate local MCP failure requires manual inspection and validation rather than durable outcome reconciliation. Shield dispatched persistence from late cancellation and keep the queue until mutation-state capture settles. Define the persisted `clean` → `pending-auto(0..2)` → `manual`/`pending-manual` validation-follow-up state machine, active-branch recovery, valid-only reset, and no-reset behavior for unresolved mutations and lifecycle events. Record the resolver's nearest-existing-ancestor containment algorithm and repository-contained-versus-repository-escaping symlink decision, including acceptance of a `knowledge/` symlink target elsewhere in the repository. Require mutations to carry ingress and expected canonical target, re-resolve ingress at dispatch, and reject target drift before persistence. Record success with in-memory pending validation and separate manual guidance when post-apply snapshot persistence fails. Record the deliberate unreleased MCP break that replaces `sokf_read` with `sokf_resolve_source` and `sokf_retrieve`. Reject compatibility aliases, independent emulation, rendered virtual file reads, rollback after persistence, post-persistence tool errors, mutation-envelope file-tool results, counter reset before valid validation, and releasing the queue while persistence can still complete.
